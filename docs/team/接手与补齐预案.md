## 开发时就为接手准备

- 同一仓库与技术栈，模块契约、迁移、配置样例、启动/测试方法、说明在仓库内；不依赖个人聊天或私有机器才能理解。
- 每个小任务说明所属文件、基础版本、实际检查和证据、失败项、依赖、下一步。公共字段变更记录版本；凭据仅保留在本人本机。
- 各模块包含自己的后端、页面、数据库变更和测试，接手不凭截图推断完成。不另造三套接口或共享真人凭据。
- 尚未接入的依赖允许契约替身作模块测试，但必须标记；正式验收必须换成真实模块，不能以假收件/假回执/假数据结果填缺口。

## 何时考虑接手

触发条件包括：约定小任务未达到验收；本人明确无法继续；关键接口或必交材料阻塞全队；截止日倒排显示不能按时修复。首先整理证据与剩余量，原作者能修复则先返修。不能仅因没有 GitHub 账号或 Agent 已开始工作就判定其失败。

## 接手顺序

1. 取得原作者当前源码、版本/基线、未提交差异、迁移与依赖说明、实际检查、已知问题；没有远程账号时可用排除凭据/数据库的代码包和文件差异交接。
2. 记录接手任务的明确范围、文件列表与新负责人，并由用户通知原作者停止修改该范围。若不能确认停止，只能在隔离分支审查/准备，不能两边覆盖合并。
3. 保留原成果，在独立补齐分支实施，不整目录覆盖、不删表/迁移凑通过。检查公共入口、迁移多头和依赖锁冲突。
4. 做最小完整修复：对应 API/页面/数据表/测试/说明一起补；实际跑模块和主链路，失败记录复测。
5. 审查后合入共同版本，更新贡献、任务归属和材料。接手完成标准与原作者相同；不把“本地 mock 可用”改写为真实渠道或全系统通过。

## 优先级与可补任务包

优先硬性要求和主链路：B 冷库/批次最小接口、离线/数据告警与追溯、两种真实通知；C 原始保存/质量处理、查询/历史/导出；再补算法融合与效果验证；PPT/视频/设计和测试报告从开发起积累，最终必须齐全。

接手的是明确小包，如“CSV 导出与对应测试”“告警去重/处理时间线”“通知失败重试”“一个页面接真实 API”“整理已验证的测试记录”，不是笼统接走整个 B/C。算法加分部分不能牺牲硬性功能；若尚无真实实验结果，先记录欠项再验证，不编提升率。

外部邮箱/手机操作、账号授权和组委会认可仍需相应同学/用户配合；A 写代码无法替代终端实收证据。无法使用原作者秘密时重新以本人授权的测试配置验证，不索取群内明文密码。
