## 1. 为什么不全压给 A，也不整套顺序接力

三位同学对应三个持续运行的开发工作区，使用一个共同仓库、同一框架、独立本机数据库。保留完整模块所有权，但首轮只交付很小的可测部分，先固定契约再接线。不要求 A 先做完，也不让 B/C 只做最后材料。

必选功能有依赖，不能承诺某人完全不参与也不影响进度。可控办法是：首轮独立样例测试、固定字段、早期真实联调、每个小交付明确检查点；停滞任务经协调后回收，不等月底。A 不必手工读懂全部合并差异，Agent 应承担代码检查、接线、验证与记录；账号、授权、不可访问的本机操作仍由人完成。

日常配合目标是短时间查看结果、响应必要操作、回传交付，不是让 A 连续手写数小时。没有测得的人工作业时间，不承诺每天 20 分钟就够；首次安装、通知授权、跨机复现、录制和答辩需要集中时间。三个人都必须实际推进各自 Agent；不保证关闭电脑后自动继续。

## 2. 不扩大范围

两冷库、三批同一明确品种苹果、十四逻辑仿真设备；先在一个冷库的小场景打通。使用现有 FastAPI/React/TypeScript/Vite/PostgreSQL、Docker；后续 MQTT/Mosquitto、Python 仿真器。复用登录和认证，不另建三个系统，不换框架、不添加微服务。首版人工确认控制，不做复杂自动调度、路线、采购销售、独立手机 APP。

必选：注册/在线/控制/故障追溯、实时数据/清洗/历史/导出、两种真实独立告警渠道及记录、源码/可运行包/软件设计文档/测试报告/PPT/视频。

加分：Isolation Forest 和累计环境暴露与业务融合、图表和独立对比实验。10 月 23 日必选功能未全通过时停止算法扩展。已使用算法必须配套报告、代码调用关系、数据来源或生成规则/样本量/样本文件。不伪造品质概率、保质期或真实节能率。

## 4. 接口是开工条件，不是无限等待

共同依据 `contracts/INTERFACES.md`，当前仍为草案，不能冒充已实现接口。

每位 Agent 首轮先提出本模块最小 Python 服务签名、JSON 样例、校验规则、失败处理及调用位置，保存在自己模块的 `01-contract-proposal.md`。A 本对话 Agent 核对三方提案并形成带版本、样例和测试的最小契约提交。没确认的字段不要各自发明后做整套表。B 可先写通知适配器；C 可先写纯数据处理及样例测试，不等待设备、批次网页。这些测试只证明模块逻辑，不算真实链路通过。

最小对接：

- A→C：合法设备观测（message_id、device_id、warehouse_id、采样/接收时刻、metrics、schema_version）；A 验设备身份，C 校验/幂等/保留原始值/存储。
- A→B：离线/恢复/故障候选，含来源 ID、设备/冷库、发生时刻、原因。
- C→B：阈值/风险候选，含来源 ID、观测依据、对象、严重度、算法版本。
- B→C：只读批次/规则版本快照。无规则显示待配置，不自造阈值；首轮可用明确标注的固定测试规则。
- C→页面：统一实时/历史/质量/导出；B 不另造数据源。
- A→B：控制记录只读引用，含 command_id、执行/失败/超时状态；Broker 收到不是设备执行。

仓库、设备表关联和未知仓库校验由 A/B 接线时确认。不得绕开现有 A01 的“尚不允许绑定”校验自行认为已绑定。

## 7. 每个小交付怎么回传

用户不希望频繁督促或转述。进度和交付直接写共同 GitHub 角色 Issue/PR，由各负责人/获授权 Agent 维护；S0 #5、E1 #6、A #7、B #8、C #9 已建立，现有 PR 包括 #4/#10/#11。具体操作见 `05-新手操作与两个检查点.md` 和持续执行总任务。账号/网络不可访问时如实报告；读取任务记录不等于 Agent 自动被唤醒。

优先自己的功能分支＋PR（或分支/提交链接），不得自行合并 main；没有 Git 时先用不含私密文件的代码包，保留目录和变更清单。PR 只表示待审核，不表示合并或验收。

固定五项：代码版本与文件；实际完成项；测试输入/预期/实际/证据；未完成项/阻塞；共享文件或契约变化。

交付状态只用：未开始、开发中、待接线、待验收、验收通过。模块测试通过、联网服务接受、终端实收、完整联调分别记录。二次通知需要接收人授权及组委会认可；两邮箱和站内弹窗不算两种。

卡住一次就记录并回传，不要悄悄等待数天。A 协调把停滞任务明确转交，先保原作者代码、通知其暂停同一范围，再在新分支接手；默认不全压给 A，先看另一个工作区是否能接。任何人长期不参与都可能影响截止目标。
