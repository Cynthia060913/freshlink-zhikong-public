## 1. 最终做成什么

同一套冷链仓储系统：两冷库、三批同品种苹果、十四逻辑仿真设备。先用一库、一温度测点、一执行器打通，再扩目标场景。仿真必须说明来源/生成规则，不称真实硬件实测。

一个用户实际操作的主线：登记仓库/入库批次并配置有来源的版本化规则 → 注册绑定设备 → 仿真器持续上报/心跳 → 看实时值和质量 → 升温或停心跳触发告警 → 邮箱和第二独立渠道实收 → 人工确认并发制冷命令 → 设备执行回执与后续温度变化 → 恢复但保留历史 → 按同一筛选查历史/导出 → 从告警追到观测、规则、处置和控制。

“最低合格”是通知全部必选功能加必交材料；“完整目标”再加业务化的风险/暴露指标、可复现模型对比和效果图。没有必选闭环时不优先做模型、动画、大屏。算法非强制；若采用，则不能独立于系统，须交配套报告/代码/数据。不做硬件PCB、自研独立手机APP、运输销售或多品种大平台。

## 4. 服务器：本地先合格，云端是可选部署

服务器就是运行后端服务/数据库的电脑，不一定是租来的机器。现在A电脑的Docker已运行网页/API和PostgreSQL；MQTT/仿真器是后续服务，不因当前模板启动就称已运行。

| 部件 | 做什么 | 开发/交付安排 |
|---|---|---|
| React页面 | 用户看数据、登记、处置/控制 | 由现有应用提供，不另建三套站点 |
| FastAPI | 鉴权、模块API/业务服务 | A/B/C代码合并成同一应用 |
| PostgreSQL | 设备、业务、数据/事件持久化 | 三人开发时各自数据库；集成时同一实例；GitHub不存数据库 |
| MQTT/Mosquitto | 仿真设备消息收发 | A负责配置/主题/身份，集成前验证；数据库和broker不直接暴露公网 |
| 仿真器 | 采样、心跳、执行控制并改变后续数据 | A提供安全初始化/固定场景/种子和运行方法 |
| 邮件/APP服务 | 把告警送到终端 | B接入；本地系统需相应互联网连通和持有人授权，不因此必需云服务器 |

`localhost:18000`只指当前电脑；队友看A的GitHub不等于能打开A电脑服务。并行代码与进度用GitHub，集成先A电脑运行，第二电脑同包复现。后续若要求公网访问再在本人确认预算/提供商/安全设置后评估部署；通知只说明服务器不报销，未要求所有软件作品购买云服务。不能默认GitHub托管完整后端或共享实时数据库。

本地交付仍需可运行应用/发布包或镜像、无秘密配置样例、准确启动/停止/演示/数据生成说明、依赖版本、联网与离线限制、另一电脑实际运行证据。代码压缩包和Docker已安装都不自动证明“可运行应用”合格；交付形式若群有补充，以补充为准。不为方便关闭证书验证/防火墙，不未经同意开放端口、购买云服务或上传数据库。
