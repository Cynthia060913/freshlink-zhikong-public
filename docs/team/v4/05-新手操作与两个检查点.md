## 1. 你现在发的群消息

使用本目录 `06-可转发群消息.md`，只发送“现在发”一节。不把未发布的基础写成已发布。不发送个人密码/邮箱授权码/Token/.env.freshlink。

B/C 可以先接入、保护旧成果、检查环境、做首轮提案和纯适配器/逻辑；未确认契约前不自造完整接口和数据库。B/C 各自维护主 Issue，代码阶段保存在各自分支；A 不逐项催促。

只用 Issues + PR，暂不要求新手再配置 Projects 看板。Issue 是任务记录，PR 是要合并的代码；Commit 是某次代码快照，main 是共同稳定版。分支可以先公开给队友看，并不表示已进入 main。

浏览器进入共同仓库→Issues→New issue（有模板时选适当模板/空白项）→复制相应文件标题和正文→Submit new issue/Create。Assignees 选真实 GitHub 用户，用户名未知则先空着，后补。B/C 也可创建自己的主 Issue，不必由 A 包办。

如果没有 Issues 页，仓库所有者查 Settings→General→Features 的 Issues 是否开启。界面文字可变化，不点击不明外部链接。旧 Issue 已存在先查看、补充，避免重复。创建成功记录真实 URL/编号；本文不虚构 #1/#2。

每人的补充评论使用：任务/基础提交/分支PR/已测/未测/阻塞/下一步。不在他人分支更新自己的状态文件制造冲突。小 PR 关联自己的主任务时用 `Refs #实际编号`；只完成其中一部分，不写 `Closes #主任务` 让整块误关闭。最终整块验收才关闭主 Issue。

## 3. 共同起点 S0 的判断标准

S0 分“代码起点”和“接口起点”，是一个共同开工检查点，不是只收到账号。

### 代码起点

1. A01 和 v4 经检查后保存到分支、推送并审核进入 main；保留现有成果，不强推/重置。
2. A 公布这次真实 main 的完整 commit SHA。B/C 从更新后的 main 开自己的分支；自己分支的 HEAD 随开发改变，不能要求之后一直等于基线。
3. B/C 确认新基线是自己分支祖先，可由 Agent 运行 `git merge-base --is-ancestor <真实基线SHA> HEAD`（exit 0 表示包含）；不要把占位符当命令执行。
4. 三人 origin 指向同一仓库；启动同版基础，API/login 检查通过，至少本人实际打开一次 /devices；密码本机独立。
5. 每人把无秘密的确认表作为 S0 评论，不回传 .env 或完整未脱敏日志。

### 接口起点

6. 三方基于当前草案提交最小签名、JSON 样例、ID/时间/单位/错误/幂等行为及调用位置；A 本对话 Agent 检查一致性，形成版本化契约及小测试的提交。
7. B/C 获取这个契约提交，在 S0 确认兼容；从此变更约定走 PR/记录，不私自改字段。

满足 1—5 可认为共用代码已就绪，可做首轮独立适配器/处理测试；1—7 全部有证据才关闭 S0 并大规模开发业务。本文不把未实现的服务当作已经存在，不因签名一致就算真链路通过。

确认表由每位 Agent 生成，本人检查自己能登录即可：

```text
角色/用户名：
origin：
共同基线SHA：
本角色分支/HEAD：
包含共同基线：是/否（实际检查）
契约版本/提交：待确认或真实版本
环境检查：通过/失败
基础启动/API登录：通过/失败/未运行
本人 /devices 浏览：通过/未检查
旧成果已保护：是/无旧成果/未完成
阻塞和证据（脱敏）：
```

## 4. 早期联调 E1 的判断标准

目标 10 月 15—17 日；这是计划节点而非保证。无需 B/C 全部功能做完，但最小版本必须有可测输入/输出及说明。由一个指定集成 Agent 处理共享入口、导航和迁移顺序，各作者修自己的模块。

提前准备：A 最小合法观测/心跳/制冷命令回执；B 一个冷库/批次/规则、候选接收、两个获准通知；C 原始保存/质量标记/查询/CSV/阈值候选。接收账号和手机由本人授权，第二渠道资格尽早确认。通知尚不就绪可先测其他步骤，E1 写部分通过，不能宣称全链通过。

只在一台电脑本地演示，代码来自已记录的集成提交、数据库保持独立。不是把三个数据库拼起来，不是把 A 的本地 localhost 地址发给远端 B/C（他们访问的是自己的电脑）。数据通过软件里的模块链路连接，不要求三台电脑都同时运行并跨公网组网。

最低步骤：

1. 一个冷库、一个批次、一个温度测点和一个制冷执行器就足够；记录对象 ID/规则，仿真标签明确。
2. 仿真器经 MQTT 合法上传，设备心跳更新，C 存储 raw/quality，网页显示对应观测与采样时刻。
3. 固定场景触发真实仿真升温，C 阈值候选传 B；告警记录有来源 ID、观测依据和对象。高温保留，不被清洗掉。
4. B 发两个获准独立通知，分别核对服务状态和终端实收；保留脱敏证据。
5. A 页面下发制冷命令，记录 command_id；执行器返回真实 ACK，未来仿真温度改变；不能用 Broker 收到代替执行。
6. 查询告警→原始观测→处理→控制→恢复记录；导出同一时间段 CSV 核对值/单位/记录数。
7. 停止测点心跳，等已配置离线阈值，验证离线候选/告警；恢复后状态正确。

每步填预期/实际/版本/对象/时间/证据和未覆盖项。最后 E1 报告仅在全部步骤通过后写完整通过。PR 自动检查即使全绿也不能证明实际手机实收和全链通过。

模块问题在对应 A/B/C Issue 或 PR 留复现和证据，不由 A 人工复制到群里；需要本人提供权限/手机时才通知本人。没有远程访问授权的 Agent 无法自动读写私有仓库，需本机本人完成认证或暂时回传，不承诺天然自动通信。

## 5. 你怎样继续 A

顺序固定：

1. 不重新安装环境：检查现有差异/测试证据/秘密忽略→保存 A01/v4/本指南→推任务分支→检查PR→进入main→公布基线。
2. 本对话继续 A 的契约提案/最小仿真与通信；B/C 同时做自己的首轮，不等待他们全部完成。
3. Agent 继续前查看共同 Issue/PR/基线状态，不要求本人每天手动转述；需要 GitHub 身份/网络工具权限就明确请求本人操作。
4. 进入 E1 后一次只合并一个可测小交付，不同时启动三套完整重构。基础迁移先 A01 再 B 最小仓储再 C 最小数据，当前 head 为准。
5. E1 通过后各作者自行补本模块，10 月 23 日必选检查；10 月 28 日发布材料同版；29—31 日修复。

你只需：首次邀请和授权、确认自己的操作结果、参加早期实收/控制验证和最终演示。看 GitHub 可以了解进度，但状态不会凭空更新，模块作者/授权 Agent 必须维护。未运行的工具、未设置的 CI/看板不写已完成。

## 6. 本人执行 Git 操作的安全顺序

当前本机分支为 feature/a-device-minimal。先由 Agent 核对全部变更和私密文件，给出明确 stage 清单，再 stage/commit；不使用盲目 `git add .`、force push、reset --hard 或删数据库。可在有经检查的本地提交后推此分支：

```powershell
git -c http.sslBackend=schannel push -u origin feature/a-device-minimal
```

之后在 GitHub 发 PR（base main、compare feature/a-device-minimal）并检查。不要点击 Deploy/Codespaces，不需要云服务器。main 合并后确认实际远程main提交号才公布基线，本地旧origin/main未fetch不能当远程最新。

这份指南不包含未核对的长串 stage/commit 命令，避免新手把不明改动全部上传。下一执行阶段会给一次经检查、范围明确的保存操作，或在授权与权限允许时直接执行。
