## 实际失败、修复和复测

1. PowerShell 7 的中文源码 ZIP 正向和12种损坏负向通过；首次受限环境启动 Windows
   PowerShell 5.1 被授权管理拦截，未调整执行策略。正常本地运行随后发现缺显式
   `System.IO.Compression` 类型加载，已修；5.1和7均实际通过同一组守卫。
2. 首个短目录独立入口发现默认包目录参数绑定为空。改为参数绑定后读取脚本目录，
   并加入“复制实际入口/守卫到合成包，不传 Package 参数”的回归，5.1/7均通过。
3. 第二次真实包运行，业务证明已生成，但5.1把 `docker logs` 的 Alembic INFO stderr
   包装成终止错误；主脚本如实退出1，清理0，证据保留，不能把它写成整体成功。
   现仅在日志收集范围保留原始 stderr 文本，同时分别检查 logs 与业务进程退出码；
   不忽略业务失败，也不全局放宽错误处理。
4. 最终固定 cb88 工具在无 Git 元数据、含中文/空格的另一短目录，**Windows PowerShell
   5.1 实际载入三镜像→空 PG 正式 C01 / model check→14设备分段→保存日志→清理通过**。
   proof_exit=0、cleanup_exit=0，容器/网络按独占标签回读为空。Compose 清理输出有一次
   重复 runner 停止告警，CLI退出0且最终资源回读为空，告警保留，不伪称没有任何警告。

最终业务结果：两库三批、14在线、7采集流、7执行 ACK 后新降温样本；14设备停发离线
后恢复在线并关联原事件，SQLite执行计数仍1，C旧历史保留；两库 snapshot CSV 40/30行，
完整 observation ID 集合分别与同筛选持久行一致。离线阈值3秒是测试值，生产90秒不变。
