# A22 同设备未结前驱阻挡候选

仅修改 A 队列选择、自己的测试和本说明。不修改 B/C 业务、正式迁移、表结构或契约。
本候选不是正式发布、C 提交前沿或完整 E1。

## 问题与改动

原 `claim_next` 仅从当时可领取的 queued/过期 leased 行排序。某设备较早观测
正在退避、持有有效租约、blocked 或 exhausted 时，较后观测仍可能先送达 C。
C 按可信接收时间推进恢复水位时，这可能让较早但较晚提交的坏观测落到水位后。

现在先要求不存在同设备更早的未结 inbox 行，再考虑领取资格；顺序键为
`(received_at, reception_id)`。前驱查询包含所有 inbox 状态，不仅包括可领取行。
现有短事务 queue_guard 继续串行化领取决定，不把 A 锁跨越 C 调用。

- 同设备：有效租约、退避、blocked、exhausted 均阻挡后续行；不删除原始数据。
- 其他设备：仍可领取自己的首行，不因一个坏设备全队停发。
- 过期租约：重新领取原前驱、保持原 reception_id 与预算；不先领取后行。
- 已确认终态：C 回执通过校验，A 原子记录终态/移除该 inbox 行，后行才解除阻挡。
- blocked/exhausted：由现有管理员显式重试处理；不为提高吞吐量跳过坏证据。

## 尚不能据此宣称的能力

1. 这不是完整 C commit frontier。租约不会取消已运行的旧 C 调用；相同 reception
   的并发投递仍依赖 C 的真实唯一约束、事务和幂等性，不能仅凭 A 租约推断完成。
2. 新接纳观测可能带有比已提交观测更早的服务器时间；相同接收时间时，A 的
   reception UUID 与 C 的 observation UUID 也不是同一排序键。仅 FIFO 不解决这些
   边界，需 A/C 同版确认前沿、晚提交补偿或保守不恢复策略后再启用持续自动恢复。
3. `invalid/conflict` 是有追溯的终态，不代表正常业务样本；不能由 A 删除原队列
   行推断 C 已把该行正确计入恢复证据。
4. blocked/exhausted 可能持续阻挡该设备并使有界队列背压，这是保留坏证据的
   明确取舍，需管理员排错；本候选没有新增告警页面或跳过/删行操作。
5. 查询在现有最多 1000 行有界 inbox 上执行，没有擅改 A04 已批准的迁移或加索引。
   不据此宣称生产规模吞吐量、容器重启、跨机、真实双通知或 E1 验收。
