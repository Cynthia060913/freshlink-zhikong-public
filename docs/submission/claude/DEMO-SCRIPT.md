依据固定提交 `96afaab8ef5a26725a0fa31ff4ff3fc4983698bf`。按“讲什么 → 屏幕做什么 →
输入什么 → 预期出现什么 → 证明哪条要求 → 源码/证据依据”组织。**页面与按钮名来自当前前端
源码，不是虚构**；未实现/未验证的镜头标“待完成后录制”。实际录制的同版 SHA 与最终素材须

## 场景 1：范围（两库、三批、十四逻辑设备）

- 讲：两座苹果冷库、三批同品种苹果；七个测区，每区一个温度采集身份 + 一个制冷执行身份，
  共 14 个**软件仿真**逻辑设备；不是硬件采购，不是真实果品品质实验。
- 屏幕做：展示项目结构/运行说明或首页。
- 预期：画面出现“软件仿真设备”与两库三批范围的文字。
- 证明：比赛必选“设备/冷库/批次范围”与“软件仿真不冒充物理测量”。
- 依据：`docs/submission/A-SYSTEM-DESIGN.md` §1。

## 场景 2：设备注册与在线/离线

- 讲：设备要先登记、再由冷库绑定；在线状态来自服务端保存的心跳结果，不是页面猜测。
- 屏幕做：`/devices`（设备管理）→ 注册设备。
- 输入：设备编号、设备名称、设备类型（按实际登记值）。
- 预期：出现“已注册 …；尚未收到心跳，不能判定在线”；列表显示绑定冷库与连接状态。
- 证明：注册权限、绑定、在线/离线判定；同时说明“在线 ≠ 温湿度正常”。
- 依据：`frontend/src/features/devices/DevicesPage.tsx`；`backend/app/modules/iot/routes.py`
  与 `binding_routes.py`（`/api/v1/devices`）。

## 场景 3：实时数据与质量处理

- 讲：设备持续上报原始温度，C 在同一事务保存 raw 与质量标记；原始记录保留、不清洗掉。
- 屏幕做：`/telemetry`（遥测历史）查看最新观测与质量。
- 输入：选择已提交设备/冷库筛选。
- 预期：最新观测含 raw_text 与质量标记；说明“风险提示不代表所有批次已判正常”。
- 证明：实时采集、原始记录、质量处理。
- 依据：`frontend/src/features/telemetry/TelemetryPage.tsx`；`backend/app/modules/telemetry/`
  观测与质量（`/api/v1/telemetry/observations`）。

## 场景 4：历史筛选与同快照 CSV

- 讲：同一次查询的分页和 CSV 用固定快照，刷新筛选才建新快照，保证导出一致。
- 屏幕做：`/telemetry` → “按筛选新建快照” → “导出本次快照 CSV”。
- 输入：筛选条件 + 点击导出。
- 预期：列表显示“固定快照共 N 条”；CSV 与当前分页来自同一快照。
- 证明：历史查询与同快照导出（必选“历史/导出”）。
- 依据：同场景 3 的 `TelemetryPage.tsx`；`modules/telemetry/snapshot_candidate.py`。

## 场景 5：异常、人工处置与追溯

- 讲：阈值异常按生效规则生成事件；人工处置后有状态变化和时间线，历史暴露不被删除。
- 屏幕做：`/alerts`（告警处置）查看事件、处置并回看追溯。
- 输入：按实际事件处置。
- 预期：异常事件、处置动作与时间线可回看；原始超温与历史仍保留。
- 证明：告警可追溯（必选“故障溯源”）。
- 依据：`frontend/src/features/alerts/AlertsPage.tsx`；`backend/app/modules/alerts/models/event.py`
  与 `status_transition`。

## 场景 6：控制指令、设备 ACK 与后续数据

- 讲：人工下发制冷命令，经 MQTT 到设备执行，服务端以**设备回执**为准，再回看后续温度。
- 屏幕做：设备页“远程制冷控制” → 选开启/关闭制冷 → 设命令有效期 → 确认。
- 输入：开启制冷 + 有效期。
- 预期：命令进入“最近 5 条命令”；服务端保存的设备回执出现；后续温度采样反映制冷效果。
- 证明：控制与设备执行 ACK（必选“控制”）；页面显示“发送”不等于已执行。
- 依据：`frontend/src/features/devices/DeviceControlPanel.tsx`；
  `backend/app/modules/iot/control_routes.py` + `simulator_runtime.py` 原 ACK 路径。

## 场景 7：设备重连与重启（模拟器侧，不等于异常恢复）

- 讲：这是**模拟器重启/设备重连**的恢复：重启后重发原采样/ACK，超 60 秒停机显式记录
  restart_gap，温度冻结、制冷关闭，需新命令；历史不清零、不补造缺口观测。它**不是**温度异常
  的恢复业务。
- 屏幕做：演示重启设备后回到遥测/告警看恢复记录与历史仍在。
- 输入：重启设备（受控）。
- 预期：出现恢复记录与保留的历史；说明“数据不足不判正常”。
- 证明：设备侧重启恢复与历史不清零。
- 依据：`simulator/README.md` 关键行为；`docs/modules/A/05-continuous-runtime.md`。

## 场景 7b：异常恢复与关联追溯（**待完成/待录**）

- 讲：原温度异常在**有效证据窗口之后**恢复，服务端保留该异常与关联追溯，恢复关闭异常也不删除
  原始超温与历史暴露。该业务镜头尚未在同版实测，当前不录、不预填结果。
- 屏幕做：`/alerts` 回看一条原异常的恢复与关联追溯。
- 输入：无（需同版实测后补）。
- 预期：异常状态变化、恢复时间线、关联证据与保留的超温历史可回看。
- 证明：异常恢复与关联追溯（必选“故障溯源/恢复”）。
- 依据：`docs/submission/A-SYSTEM-DESIGN.md` §3 异常恢复要求；同版实测通过前标“待完成/待录”。

## 场景 8：邮件与飞书两种终端实收（**待实收后录制**）

- 屏幕做：分别展示脱敏的邮箱与飞书手机端收件证据。
- 输入：无（实收由持有人本机授权并确认）。
- 预期：两渠道各自出现实收；录制前先按 `CAPTURE-PRIVACY.md` 遮挡账号/授权码/二维码。
- 证明：至少两种独立通知渠道实收（必选“两通知”）。
- 依据：`docs/submission/README.md` 必选功能表；当前**尚未实收，不录假镜头**。
