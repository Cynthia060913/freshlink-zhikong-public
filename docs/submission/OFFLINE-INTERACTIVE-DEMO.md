# 离线制品的交互演示入口（交付工具候选）

应用固定为 `e7fffd61c199234918dcf1713cc1f3dd6ce78c51`，与已发布 main
`319aa6363d921922070b4330bf74e344a8b0c1bb` 的整个代码树相同。本工具在应用镜像之外
复用原有服务，不修改业务代码、迁移、原数据库或宿主 Python。工具本身的提交与
应用来源分别记录；合并此工具不等于另一次 E1 或参赛投递。

## 接收与核验

需要已经安装、启动的本机 Docker Desktop Linux amd64 引擎和 PowerShell。
不自动安装软件，不改 PATH/执行策略/全局网络，不接受远程 Docker 上下文。
本机交互实跑使用 PowerShell 7；Windows PowerShell 5.1 的执行被系统策略拒绝，
因此不宣称本入口已在 5.1 跑通，也不以 Bypass 或更改执行策略规避。接收机遇到
同样限制时使用其已获准的 PowerShell 7，或交由本人/管理员处理策略后再验证。
将交付物放新目录；先从可信的另一渠道核对外层包 SHA256，再取得内部 kit 的
offline-manifest.json 哈希。哈希是传输一致性检查，不是全面安全审计或软件签名。

包中 kit 是已核验的应用/PG/MQTT 三镜像、源码 ZIP 和旧离线业务验证入口。
delivery-tools 保持 scripts/windows 与 scripts/offline-demo-runtime.py 的相对目录；
不要仅复制一个 ps1。仅验证命令不调用 Docker：

```powershell
Set-Location -LiteralPath 'D:\FreshLink-delivery'
.\delivery-tools\scripts\windows\open-offline-demo.ps1 `
  -Kit .\kit -ExpectedManifestSha256 '另行核对的64位小写哈希'
```

## 启动页面和真实仿真采集

在相同命令后加 `-Start -Minutes 5`。每次使用新的随机项目与新建专属数据库卷，
不会接管原来的 fixed freshlink 项目。全部镜像按包内 ID 加载，原标签不覆盖。

```powershell
.\delivery-tools\scripts\windows\open-offline-demo.ps1 `
  -Kit .\kit -ExpectedManifestSha256 '另行核对的64位小写哈希' -Start -Minutes 5
```

启动会正式升级新库至 C01，并运行已有两库/三批/14 设备初始化验证；其后用同一库
启动编译在镜像内的默认 API/前端与现有 receive/store/evaluate/deliver-high 服务、
心跳/控制 worker 和七组实际模拟器。没有应用源码挂载；唯独外部交付监督脚本只读
挂载。它不造接收回执、不清旧队列、不重置已存在的 epoch。

命令输出随机的 `http://127.0.0.1:端口`、状态文件和本机密码文件位置。
登录账号为 `admin@example.com`，本轮随机密码只保存在包外的 admin-local.json，
不要分享该文件。生成的 owned-compose.json 也包含本轮随机数据库/应用秘密，
不得进入 Git、视频或参赛压缩包。测试日志对这些随机值脱敏。

页面操作：

1. 设备管理：核对 14 台逻辑设备和心跳，打开执行器查看回执；新控制需真正设备 ACK。
2. 遥测历史：按某个传感器 ID 建快照，检查新数据、保存原文和质量，再下载相同快照 CSV。
3. 告警处置：查看真实采集与历史规则形成的告警；管理员可确认，普通账号仅只读。
4. 普通账号可通过系统注册获得，不允许其下发控制或确认告警。

真实通知始终关闭，包内没有收件人/SMTP/飞书配置，不能用本入口重发已消耗授权的
E1 事件。自动恢复/更正发送也未在本演示入口启用；完整应用中的已审核显式角色与
另行实测的同事件 E1 证据分开说明，不把普通启动冒充所有角色都在运行。

## 运行时长、停机与数据

采集与设备运行默认 5 分钟，允许 1—10 分钟；它是受控演示窗口，不是无限时生产
服务承诺。达到上限后停止数据角色，页面保留，陈旧/离线提示按实际状态显示。
模拟器与数据库都有有限容量；不为继续演示删除原数据、轮换 epoch 或扩大配额。

停止时使用启动输出的本轮状态文件路径：

```powershell
.\delivery-tools\scripts\windows\stop-offline-demo.ps1 `
  -State '启动输出的本轮demo-state.json完整路径'
```

停止脚本先验证随机项目名及每个容器的专属标签，再停机和移除本轮容器/网络，
不执行任意状态文件提供的 Compose，也不删除命名数据库卷、模拟器状态、其他项目
或缓存。故障启动也调用同一受限清理。数据卷保留是回退点，不等于已有无损自动
重启功能；新启动命令会创建新项目，不会偷偷把旧数据当空库初始化。

Broker 的密码文件只在其自有 /tmp tmpfs 中生成，重启不碰主机文件；接收的原始
观测日志与 PostgreSQL 持久卷是另一层，不以 Broker 的 PUBACK 冒充应用接纳。
内部 B bearer 仅通过同一应用网络命名空间的 loopback HTTP 传递，保留原 transport
对跨容器明文 bearer 的拒绝，不使用 host networking，不关闭 TLS/鉴权守卫。

## 验收边界

启动成功要求至少 14 条新增实际 C 观测，不仅是容器处于 running。还需实际登录、
观察持续增加、执行控制并取得回执、下载 CSV 和验证权限后才能记录交互通过。
失败与清理状态需真实保存，不能将异常/超时当作成功或重复启动覆盖旧证据。
此交付工具须独立审查；最终 M01—M05、第二机本人确认和实际投稿仍逐项签收。

## A 本机交付入口实测（2026-10-28）

应用来源仍为上述冻结提交。三镜像离线载入后，实际浏览器登录，14 台设备全部在线；
页面“关闭制冷”产生控制 `93c5d8b3-8569-4927-bb80-c2919b883bdd`，实际 MQTT
执行回执确认关闭；采集最新记录持续增加，下载的 15 行 CSV 与同一快照全部 ID 相同。
无 API Mock、真实外发为 0。三分钟数据窗口正常结束，四个子进程退出码均为 0，
线程清理正常。受限停机后容器、网络均为 0，保留的数据库卷有 1202 条原始观测；
随后仅重启该专属 PostgreSQL、无网络只读回查，仍为 1202 条，再停止临时容器。

验证过程保留了两次启动失败，分别修复 SQLModel 对象读取及内部 loopback 传输接点，
没有放宽原有权限或 bearer 传输守卫。浏览器初次重复申请快照遇到 429，改用已有
非快照 latest 接口验证持续采集，没有扩大每用户快照预算。另一次 Broker 重启发生在
演示采集窗口结束之后，因此本入口的重连专项没有据此写成通过。

这些结果是 A 本机的交付入口验证，不代替接收方在另一台电脑对最终外层包的复现；
已有 C 的同源应用第二机证据仍按原范围保存，不将本工具候选冒充其已执行内容。
