**重要（不得以 max_events=1 推定选中）**：`--send --max-cycles 1` 派发的是
库内**最旧的待发事件**，不是"指定批准事件"。发送前必须先用预检第 3 步的
只读 SQL 确认库内**仅有**该批准事件在待发状态；有多条 ⇒ 先清理/等待
归零再批准。

## 二、停止条件（任一满足即停，不重发）

1. 两渠道各完成 1 次尝试（无论成败）——到达次数上限即结束。
2. 服务输出 `"interrupted": true` 或退出码 1 ⇒ 停，先核对再决定。
3. 任一渠道结果不明（超时/无响应）⇒ **先核对实收端，不盲目重发**；
   重发与否由 A 重新批准，每次重发单独记录。
4. A 在手机/邮箱确认实收后即达成本次目的，不再发送。

## 三、执行与核对（A 执行，B 协助核对）

1. A 确认预检三步全过（配置可解析 / `["smtp_email","app_push"]` / 库内
   仅批准事件）。
2. A 执行上表命令；保存服务输出的 JSON 行（`pending_count`、`interrupted`、
   退出码）。
3. A 在**手机飞书**与**邮箱**分别确认是否收到；未收到不重发，先回报。
4. B 协助核对：服务侧 attempt 表记录（时间/渠道/结果）与实收端描述
   是否一致；不一致按第 2 条停止条件处理。
