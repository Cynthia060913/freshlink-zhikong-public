# F03 RC2：可追溯的单批候选提案

2026-10-14，A 集成建议，等待 B/C 签收及模块作者实现。

当前 B 的输入只含来源 ID、单批次、指标、时间和值；C 的候选包含观测、
规则和算法证据。不能通过删除追溯字段来消除结构差异。本轮优先保留
B 的单批行模型并扩充事件正文，比另建多批事件关联体系更适合最低闭环。

## 推荐输入

`schema_version=1.0`、`source_event_id`、`warehouse_id`、`batch_id`、
`observation_ids`、`metric_code`、`sampled_at`、`value`、`unit`、`kind`、
`severity`、`rule_snapshot_id`、`rule_version`、`algorithm_version`、`evidence`。

示例见 `examples/candidate-f03-rc2.json`，是待实现目标，不是现有 B 可接受输入。

- 一个候选对应一个批次、一条指标规则。多批次观测按各批次有效规则
  分别生成候选，不能对多个批次重复使用同一 `source_event_id`。
- C 为每个候选分配并持久保存唯一来源 UUID，重试不换 ID；若采用确定性
  生成，需以不可变观测/批次/规则身份生成并给出跨重启一致性测试。
- `sampled_at` 是本次候选所引用观测的发生时刻，显式时区解析后归一 UTC。
  HTTP JSON 的 ISO 字符串与内部 datetime 输入均需支持；无时区不猜测。
- 首版温度/湿度 kind 保持 `temperature_high/low`、`humidity_high/low`；
  不把规则内部 `threshold_high` 名称直接当作候选枚举。缺规则、坏采样或
  无效质量数据不得生成正常阈值候选。
- 正文保存上述全部已校验字段；规范摘要覆盖追溯字段。更换 observation
  或规则后重投同 ID 必须冲突，不能因字段被忽略而回 duplicate。
- 建议首版输入最大 32768 字节、最多 64 个 observation IDs；超过上限
  显式拒绝，不截断证据。单位及数值使用现有质量规则，不从非法原值猜测。
- B 核验批次存在且属指定仓库。真实 C 观测/规则引用的持久校验和关联读取
  由 B/C 在 C1 接线时共同补齐，尚未有数据库时不伪造外键或引用已验证。
- by-source 查询需返回完整已存证据（或明确可访问的持久证据关联），不能
  只返回事件 ID 和数值而丢掉观测、规则及算法调用身份。

## 接收与失败

首次持久成功 `accepted_new`，同键同规范内容 `accepted_duplicate`，同键不同
内容 `conflict`，显式永久拒绝 `invalid`，暂时故障 `retryable_failure`。
HTTP 为 201/200/409/422/503，暂时故障 `Retry-After: 30`。

读前置对象、幂等查找、写提交、并发冲突后读取和提交后读取均要考虑数据库
故障；不能只捕获 INSERT，不能将存储故障转换成 unknown_batch。
回应未知/超时和 by-source 404 保留原 ID 有界重试。accepted 不代表已通知。

## 三方签收所需实测

正常 ISO JSON 到 HTTP 接收、重复、修改追溯证据冲突、完整查询回读、读/写
故障、无权限、未知对象、跨仓对象、恢复引用；以同一提交及实际结果签收。
在此之前 C 可以继续 F01 原始观测持久化、质量和查询，不应暂停整个 C1。
